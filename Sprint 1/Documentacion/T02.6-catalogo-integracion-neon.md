# T02.6 — Catálogo persistente para integración Sprint 1

## Auditoría de archivo externo (21-10-2026)

`AllInstant-proyecto.zip` fue revisado sin ejecución. Su catálogo Prisma
`BranchProduct` es una implementación independiente y no usa Neon,
`DATABASE_LISTEN_URL`, pooler/direct endpoints ni las tablas de esta tarea.
Por ello no se reutilizó para diagnosticar ni corregir el 503; la evidencia del
incidente y la pendiente de comprobación HTTP local continúan siendo las
registradas en este documento. Véase `T00-auditoria-alinstant-proyecto.md`.

## Objetivo

Completar HU-02 con una fuente de verdad server-side para el catálogo que consumirá la API Next.js. La migración se limita a Neon `allinstant-dev`, rama `development`, base `neondb`; no cambia pedidos, detalle histórico, cocina, despacho ni producción.

La migración se aplicó y verificó en ese entorno el 18-10-2026. La única
habilitación posterior se limitó al producto sintético `Lomo saltado - Prueba
LM` en LM para comprobaciones de integración; SMP quedó agotada. No se
modificaron precios, descripciones o imágenes existentes.

## Conexión de desarrollo

El compute development mantiene el pooler deshabilitado. Por esa razón la API
Next.js no debe usar en desarrollo una `DATABASE_URL` cuyo host incluya
`-pooler`: esa configuración produjo `ENOTFOUND` y el 503 del catálogo. La
aplicación selecciona `DATABASE_LISTEN_URL` (directa) solo fuera de producción
después de validar que host y base coinciden con `DATABASE_URL`; producción
conserva su conexión normal. Esta decisión no expone ninguna URL de conexión al
frontend.

## Modelo aditivo

`catalogo_producto` complementa `productos` sin alterar su estructura histórica:

| Campo | Regla |
|---|---|
| `producto_id` | PK y FK a `productos`; borrado restringido. |
| `descripcion`, `imagen_url` | Metadatos opcionales de presentación; no se inventan en la semilla. |
| `precio_vigente` | `NUMERIC(12,2)` no negativo; fuente server-side para cotizaciones futuras. |
| `actualizado_en` | Se actualiza si cambia algún metadato o el precio. |

`disponibilidad_producto_sede` expresa la oferta por sede: una fila significa ofrecido, `FALSE` significa agotado y ausencia significa no ofrecido. Su PK compuesta y FKs restringidas preservan integridad. El índice `(sede_id, disponible, producto_id)` respalda consultas de catálogo por sede.

## Semilla y recuperación

La migración crea una fila de catálogo para cada producto existente sin sobrescribir entradas previas. Toma el último precio histórico únicamente como valor inicial de desarrollo y usa `0.00` cuando no hay historial. Crea asociaciones SMP/LM agotadas (`FALSE`), por lo que la migración por sí sola no habilita ventas ni modifica precios ya establecidos. Descripción e imagen quedan nulas hasta una carga editorial aprobada.

La ejecución es una transacción con `lock_timeout` y `statement_timeout`. `T02.6_reversion_catalogo_integracion.sql` es una reversión estructural protegida: falla si hay datos, para no borrar catálogo operativo. Para una recuperación posterior con datos se usará la retención/restore de Neon o una migración de datos aprobada.

Para la prueba E2E autorizada se habilita exclusivamente el producto sintético
`Lomo saltado - Prueba LM` en `LM` mediante
`Testing/T02.6_habilitar_producto_sintetico_lm.sql`. Es una operación
transaccional e idempotente que exige afectar una sola asociación; no toca SMP,
el precio ni los metadatos. `T02.6_verificacion_producto_sintetico_lm.sql`
confirma después que LM está habilitada y SMP continúa agotada.

## Contrato para backend

La consulta debe unir `disponibilidad_producto_sede d`, `sedes s`, `productos p` y `catalogo_producto c`; filtra estrictamente `s.codigo` en el servidor. `c.precio_vigente` es el único precio de cotización y se fotografía en `detalle_pedido.precio_unitario` al confirmar. No se acepta precio, total, disponibilidad ni estado del navegador. Solo `d.disponible = TRUE` puede cotizarse/comprarse, revalidado dentro de la transacción de checkout.

## BDD y verificación

- Dado un producto asociado a SMP y LM, cuando su disponibilidad cambia en SMP, entonces LM no cambia.
- Dado un producto con `disponible = FALSE`, cuando el cliente consulta o cotiza, entonces se muestra agotado y se rechaza la compra.
- Dado un precio enviado por el navegador, cuando se cotiza o confirma, entonces el servidor usa `catalogo_producto.precio_vigente`.

`Sprint 1/Testing/T02.6_verificacion_catalogo_integracion.sql` es solo lectura y comprueba objetos, restricciones, semilla y asociaciones. Su resultado confirma estructura y datos mínimos, no pruebas E2E de la API.

## Incidente de permisos e integración HTTP (21-10-2026)

Aunque T02.6 estaba aplicada y el producto sintético LM existía, la API seguía
devolviendo `503 SERVICE_UNAVAILABLE`. La conexión directa SSL sí autenticaba,
pero el rol efectivo de la aplicación no tenía SELECT sobre las dos tablas
creadas por esta tarea; PostgreSQL devolvía `42501` sobre
`disponibilidad_producto_sede`. Se aplicó en `development` el script aditivo
`Codigo/T00_privilegios_cliente_integracion.sql`, con un grupo cliente de
privilegios mínimos y sin modificar production.

Tras esa aplicación, las llamadas HTTP reales de catálogo devolvieron `200`:
LM expuso su único producto disponible (ID 5, `18.00`) y SMP el producto
ofrecido agotado. La misma revisión corrigió privilegios de INSERT requeridos
por el trigger histórico de pedidos; no se otorgó UPDATE/DELETE. El flujo E2E
posterior confirmó que la cotización y creación del pedido revalidan esta
consulta de catálogo y que la fila sigue aislada por sede.
